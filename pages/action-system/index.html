Desktop Action System

从 chat popup query 到 GUI_execute、本地 action、tool result、agent 回答的完整链路

主路径 WebSocket 工具名 GUI_execute
STANDARD PATH

Action system 是一个 client-side MCP tool handshake。

agent 以为自己调用的是 MCP tool `GUI_execute`；gateway 把这次 tool_use 标记为“需要桌面端完成”； desktop 拦截该 tool_use，执行内置或注册的 GUI action，再把结果 POST 回 gateway。等待中的 MCP handler 被 resolve 后， agent 收到 tool_result 并继续生成最终回答。

10主链路阶段，从输入到回答。
60s`GUI_execute` client-side completion 默认超时。
4+N4 个内置 action，加上前端 provider/page 注册的 action。

三条相关路径的区别

Chat popup 主路径

`ChatPopupLayer` 使用 `useAgentConversation(..., { agentConfig: { mcp_servers: ["gui_action"] }, useWebSocket: true })`。这是本页主链路。

SSE fallback

`useAgentConversation` 也有 `sendMessageReal`，走 `POST /api/agent/run` 读取 SSE。`handleSSEMessage` 和 GUI_execute 拦截逻辑是同一套。

ACP bridge

`createGuiActionMcpServer` 是 stdio MCP server；它会通过 `/api/client-tools/request` 让 gateway/ACP session 请求客户端执行 GUI action。

内置 action 能做什么
action处理函数说明
list_actionshandleListActions返回 builtin + `useActionStore.listActions()` 当前可用 action 列表。
get_action_detailhandleGetActionDetail返回指定 action 的 description、input_schema、output_schema。
read_windowhandleReadWindow用户确认后用 `html-to-image` 把 desktop root 截成 PNG，作为 image tool result 返回。
navigate_tohandleNavigateTo校验相对路由和 route registry，用户确认后通过桌面 tab/breadcrumb navigation 跳转。
action provider 和 page action 如何接入
React provider 通过 `useActionProvider(namespace, actions)` 注册到 `useActionStore`，例如 `PresentationActionProvider` 注册 `presentation.*`。 静态 page 通过 `VibenPage.actions.register()` 发 postMessage，desktop 的 `PageActionBridge` 校验 namespace/schema 后注册为 `page.<workspace>.<page>.<iframe>.<namespace>.<action>`。 agent 可以先 `list_actions` 发现这些 action，再 `get_action_detail` 获取参数结构，最后调用 `GUI_execute`。
