packages/chat/example

从日志到播放器播放完成的完整链路

这个示例应用本质上是一个会话回放器：把内置的 demoSteps 或用户加载的 Claude Code .jsonl 日志转换成 AgentMessage[]，再交给基于 requestAnimationFrame 的步骤播放器逐步注入聊天 UI。播放器遇到审批、问题、计划确认会自然暂停，用户处理后继续播放，直到最后一个 step 进入 idle。

1播放器状态机：useStepPlayer
∞消息类型由 @viben/chat 渲染扩展

架构分层

这个 example 不是后端系统，而是一个前端本地会话播放器。它的边界很清楚：解析层只产出标准消息，播放器只管时序，App 只做编排，组件库只负责展示和交互。

播放器状态机

播放器的核心设计是“条件满足才推进”。阻塞不是额外的暂停计时器，而是 reducer 和 rAF loop 共同形成的推进门禁。

PlayerState
字段 / 动作 作用 对播放完成的影响
status 取值为 idle、playing、paused。PLAY 开始推进，PAUSE 停止推进，最后一步后回到 idle。 只有 playing 才启动 rAF 推进。
stepIndex 指向下一条待播放 step。ADVANCE 成功后加 1。 达到 steps.length 后视为播放完成。
messages 已经进入主消息列表的 AgentMessage[]。 最终 UI 快照就是这个数组。
pendingApproval / pendingQuestion / pendingPlan 当前 step 声明 awaitsInteraction 时写入。 存在任意 pending 时 rAF 继续循环但不推进。
pendingUserMessages 播放中的用户消息先交给 App 判断走队列还是直接注入。 未消费前阻止继续推进，避免路由覆盖。
RESOLVE_* 用户完成审批、问题或计划确认后清空对应 pending。 下一帧满足条件后继续 ADVANCE。
关键点：NEXT_MANUAL 也会尊重 pending 交互；PREV 和 SEEK 会重建目标 index 前的消息，并清空 pending 状态。

日志解析细节

解析器只识别能被聊天组件消费的核心形态，并刻意跳过本地命令、系统提醒和重复工具调用。

parseSessionJsonl

User 行

  • 如果 content 里包含 tool_result block，则生成 tool_result 消息。
  • 普通文本 block 拼成 user 内容。
  • 剥离 <system-reminder>，跳过 <local-command 开头内容。

Assistant 行

  • thinking block 生成 thinking 消息。
  • text block 生成 text 消息。
  • tool_use block 生成 tool_use，并按 toolUseId 去重。

Folder 行

  • 选择 root 下最大的 .jsonl 作为主会话。
  • 读取 subagents/agent-*.jsonl 和 meta。
  • 从 progress 行提取 parentToolUseID 到 agentId 的映射并挂回父工具调用。

命令队列和工具忙闲

队列的判断不依赖“是否正在播放”本身，而依赖消息流中工具调用是否闭合。这样慢工具、拆开的 tool_use/tool_result、用户中途输入都能表现出真实的智能体忙碌状态。

tool_use ↔ tool_result

忙闲判断

  • 扫描当前 player.messages。
  • 遇到 tool_use，把 toolUseId 放入 pending set。
  • 遇到同 id 的 tool_result，从 pending set 删除。
  • set 非空即 agentBusy = true。

用户消息路由

  • 播放器把播放中的 user 消息放入 pendingUserMessages。
  • App effect 读取 agentBusy。
  • busy 时调用 commandQueue.send，消息显示在 CommandQueuePanel。
  • idle 时调用 player.injectMessage 直接进入消息列表。

播放完成的准确定义

播放完成不是“最后一条消息渲染了”这么简单，而是所有 step 都已经成功推进，并且没有未处理的 pending 用户路由或阻塞交互。

status: idle

完成条件

  • status === "playing" 时 rAF loop 持续检查。
  • 当前 step 的 delay 已按 speed 折算并到期。
  • 没有 approval、question、plan pending。
  • 没有 pendingUserMessages 等待 App 路由。
  • 最后一次 ADVANCE 后 newIndex >= steps.length，status 变 idle。

完成后的 UI 状态

  • MessageList 保留所有已播放消息。
  • isStreaming 为 false，ChatInput 回到普通输入状态。
  • 进度显示为 totalSteps/totalSteps。
  • 用户可 replay、prev、seek 或重新加载日志。
