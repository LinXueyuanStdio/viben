Research memo · Viben Evo

用蒙特卡洛式搜索、记忆归因和多智能体评估驱动代码库自我进化

目标是把代码库版本 (c, s) 当作可搜索状态，把 idea 当作边，把 agent 实现与评测当作 rollout， 通过最少的昂贵评估步数找到最高分代码版本。结论：应在现有 viben evo 的 FileEvo/PPO 闭环上增加 BOHB/Hyperband 预算调度、MCTS 路径选择、MAP-Elites archive 与 idea 级记忆归因。

1. 问题建模

代码库自我进化可以被建成一个带噪声、评估昂贵、可并行、可早停的黑盒优化问题。 状态是代码库版本和分数 (c_t, s_t)，动作是 idea 或编辑策略 i_t， 转移由 agent 在 worktree/fork 中实现，评估器给出新分数 s_{t+1}。

状态(c0, s0)
当前代码库、基线分数、历史上下文
展开生成多个 idea，形成横向候选
rollout每个 idea fork 多份，多个 agent 独立实现
评估分层 evaluator 计算 s1 与风险
记忆归因分数增量，更新 archive 并决定下一步

横向搜索

c0 -> c1, c0 -> c2, c0 -> c3

同一代码库版本生成多个 idea，适合冷启动、探索不同模块、评估多个 prompt/operator。优点是并行效率高；风险是对每个方向的深挖不足。

纵向搜索

c0 -> c1 -> c2 -> c3

沿着高潜力版本连续迭代，适合多步重构、性能优化、测试补强。优点是能发现组合收益；风险是过早进入局部最优。

搜索目标：在预算 B 内最大化 E[max s(c)]，同时最小化失败率、回滚成本和不可审计修改。

2. 算法地图

单一算法不足以覆盖代码库进化。更稳的结构是把不同算法放在不同层：MCTS 规划路径， Bandit/Hyperband 分配预算，Bayesian Optimization 学习候选价值，Evolutionary Archive 维持多样性。

方法 在本问题中的角色 适合控制的对象 主要风险
Monte Carlo / Random Search 冷启动 baseline，大量采样 idea 或 patch。 初始 idea 池、prompt 变体、轻量改动。 样本效率低，高分候选稀疏时浪费预算。
MCTS / UCT 把多轮 edit path 建成搜索树，用 UCB 在探索和利用间平衡。 从哪个 codebase 版本继续、展开哪个 idea lineage。 rollout 昂贵，价值估计受 evaluator 噪声影响。
Multi-Armed Bandit 在线选择最有效的 agent、模型、prompt、mutation operator。 生成器、执行器、测试层级、模块类别。 难以直接利用候选之间的结构相似性。
Successive Halving / Hyperband 先用低成本评估筛掉差候选，把完整预算给强候选。 lint -> typecheck -> targeted tests -> full tests -> benchmark。 早期指标若弱相关，会误杀慢热候选。
Bayesian Optimization / BOHB 用 surrogate model 预测候选收益与不确定性，提高样本效率。 idea 特征、模块、diff 大小、agent 参数、reward 权重。 代码空间高维离散，需要好的特征化和冷启动数据。
Evolutionary / MAP-Elites 保留质量和多样性，避免只追逐全局当前第一名。 archive、islands、novelty、patch recombination。 评估次数多；若 evaluator 弱，会积累投机 patch。
推荐组合： BOHB-style controller + Hyperband evaluation ladder + MCTS lineage planning + MAP-Elites archive。 这比“每轮生成 B 个 idea，跑完后选最高分”更适合昂贵评估和长期自我进化。

3. 具体方法的算法细节

下面把每种方法展开成可落地的控制器逻辑。统一记号：c 是代码库版本， i 是 idea 或编辑动作，s 是评估分数，r 是评估预算， x 是候选 patch、prompt、模型或 operator 组合。

Monte Carlo 随机采样评估

Monte Carlo 的作用是建立 baseline：对同一个 idea 生成多个 patch 样本，运行评估， 用均值、方差和 best score 判断这个方向是否值得继续投入。

  • N：采样次数，对应某个 idea 的 rollout 数。
  • R：单次回报，对应 score(candidate) - score(parent)。
  • Q：平均收益，用来估计 idea family 的稳定价值。
  • B：预算，可以是 token、CI 分钟、并发任务数。
function monte_carlo_evaluate(codebase, idea, budget):
    scores = []

    repeat budget times:
        patch = generate_patch(codebase, idea)
        candidate = apply_patch_copy(codebase, patch)
        score = evaluate(candidate)
        scores.append(score)

    return {
        mean_score: mean(scores),
        variance: variance(scores),
        best_score: max(scores),
        best_patch: argmax_patch(scores)
    }

在 viben evo 中，它对应 rollout.n：同一个 idea 可以被多个 agent 实现。 工程上应固定随机种子、隔离 worktree、缓存相同 patch 的评估结果，并把失败原因作为结构化字段保存。

Bandit UCB 与 Thompson Sampling

Multi-Armed Bandit 把 idea family、模型、prompt、mutation operator 或 evaluator ladder 看作 arm。 目标是在有限预算内最大化累计收益，同时保留对新方向的探索。

UCB1 选择公式：

UCB_i = Q_i + c * sqrt(ln(t) / n_i)

Thompson Sampling 为每个 arm 维护后验分布，二值成功率场景可用 Beta(alpha, beta)： 成功则 alpha += 1，失败则 beta += 1。 

function bandit_search(codebase, arms, total_budget):
    initialize n[i] = 0, Q[i] = 0

    for t in 1..total_budget:
        if any n[i] == 0:
            arm = first_untried_arm()
        else:
            arm = argmax_i Q[i] + c * sqrt(log(t) / n[i])

        idea = sample_idea_from_arm(arm)
        reward = rollout_and_evaluate(codebase, idea)

        n[arm] += 1
        Q[arm] += (reward - Q[arm]) / n[arm]

    return best_observed_candidate()

对代码库演化，reward 是非平稳的：代码变了，某类 idea 的收益分布也会变。 因此统计量要支持滑动窗口、时间衰减，或按 codebase node 分开记录。

MCTS / UCT 多步 idea 路径规划

MCTS 把多轮演化建成搜索树：节点是 codebase snapshot，边是 idea/patch。 标准循环是 selection、expansion、simulation、backpropagation。

UCT 选择公式：

UCT(c, i) = Q(c, i) + k * sqrt(ln N(c) / N(c, i))
  • Q(c,i)：idea 在该代码版本上的平均收益。
  • N(c)：该代码版本被访问次数。
  • N(c,i)：该 idea 被尝试次数。
  • k：探索强度。
function mcts(root_codebase, budget):
    root = Node(root_codebase)

    repeat budget times:
        path = []
        node = root

        while node.fully_expanded and not terminal(node):
            idea = select_uct(node)
            path.append((node, idea))
            node = child(node, idea)

        if not terminal(node):
            idea = propose_new_idea(node.codebase)
            child = apply_and_score(node.codebase, idea)
            node = add_child(node, idea, child)

        reward = rollout(node.codebase)

        for (visited, idea) in path:
            update_stats(visited, idea, reward)

    return best_child(root)

工程关键是不要复制完整仓库作为节点。更合理的节点表示是 base_commit + patch_stack + metadata，并用 transposition table 合并等价状态。 对分支极多的节点使用 progressive widening，避免一次展开太多 idea。

Successive Halving 分层淘汰

Successive Halving 先用极低预算评估大量候选，每轮保留前 1 / eta， 并把幸存候选的预算乘以 eta。它适合完整 CI 很贵、但低成本信号有用的场景。

  • r0：最小有意义预算，例如 parse + affected typecheck。
  • R：最大预算，例如 full build + full tests。
  • eta：淘汰倍率，常用 3 或 4。
function successive_halving(candidates, r0, R, eta):
    S = candidates
    r = r0

    while r <= R and size(S) > 1:
        results = []
        for x in S:
            y = evaluate_patch(x, budget = r)
            results.append((x, y))

        S = top ceil(size(S) / eta) by score
        r = r * eta

    return best_full_evaluation(S)

早停不是证明 patch 差，而是在足够高置信度下判断“继续评估不划算”。 编译失败、关键测试失败、安全回归可以立即停止；flaky test、benchmark 抖动则应复评或延迟淘汰。

Hyperband 多 bracket 预算分配

Hyperband 解决 Successive Halving 的核心超参问题：到底应该多试候选、少给预算， 还是少试候选、深度验证。它运行多个 bracket，覆盖不同探索深度。 

s_max = floor(log_eta(R))
B = (s_max + 1) * R
n = ceil((B / R) * eta^s / (s + 1))
r = R * eta^(-s)
function hyperband(R, eta):
    s_max = floor(log(R) / log(eta))
    B = (s_max + 1) * R

    for s in range(s_max, -1, -1):
        n = ceil((B / R) * eta^s / (s + 1))
        r = R * eta^(-s)
        S = sample_patches(n)

        for j in 0..s:
            budget = r * eta^j
            score_all(S, budget)
            S = top floor(size(S) / eta)

    return best_patch_observed()

对 viben evo，bracket 可以直接映射为 queue 中的一组 task： 一个 bracket 负责“海量 idea 快速粗筛”，另一个 bracket 负责“少量 idea 深度验证”。

Bayesian Optimization / BOHB 用历史结果指导采样

Bayesian Optimization 用代理模型预测候选 patch 的分数和不确定性，再用 acquisition function 选下一步。 BOHB 把 BO 与 Hyperband 结合：Hyperband 管预算，BO 管采样。 

UCB(x) = mu(x) + kappa * sigma(x)
EI(x) = E[max(f(x) - f(best), 0)]

BOHB 的 TPE/KDE 风格候选选择：

D_good = top q% observations
D_bad  = remaining observations
choose x that maximizes l(x) / g(x)
function bohb(R, eta):
    history = []

    while budget_remains:
        bracket = choose_hyperband_bracket()
        r, n = bracket_schedule(bracket, R, eta)

        S = []
        for k in 1..n:
            if enough_data(history, budget = r):
                x = sample_by_surrogate(history, budget = r)
            else:
                x = sample_random_patch()
            S.append(x)

        successive_halving_with_history(S, r, R, eta, history)

    return best_high_budget_patch(history)

Patch 特征应结构化保存：diff 行数、修改文件类型、触达核心路径、失败测试类别、 静态分析结果、embedding、prompt、模型、temperature、repair strategy。

Evolutionary Algorithms / Genetic Programming 代码作为可进化个体

进化式方法把候选代码表示为个体。genotype 是 patch、AST edit 或 function rewrite； phenotype 是应用 patch 后的完整 repo。LLM 可以作为 mutation operator，evaluator 是 selection pressure。 

Individual = {
  base_commit,
  patch,
  touched_files,
  parent_ids,
  prompt,
  model,
  mutation_type,
  metrics
}
function evolutionary_loop(population):
    while budget_remains:
        parents = select(population, archive)

        if random() < crossover_rate:
            child = crossover(parents)
        else:
            child = mutate(parents[0])

        result = evaluate(child)

        if result.hard_constraints_pass:
            archive.update(child, result.metrics)
            population = environmental_selection(
                population + [child],
                method = pareto_or_fitness
            )

    return archive.best()

Mutation 包括 localized fix、performance rewrite、simplify、parameter tune、defensive patch。 Crossover 在代码库中要保守，优先做互不冲突 diff 合并，或让 LLM 基于两个父代 diff 生成语义重组版本。

MAP-Elites / Islands 质量多样性 archive

MAP-Elites 不只保留全局第一名，而是按行为特征分桶，每个桶保留一个 elite。 这能保留“高性能但复杂”“小 diff 但收益中等”“覆盖边界条件好”等不同 stepping stones。

  • diff_size_bucket：tiny / small / medium / large。
  • touched_area：parser / scheduler / cache / UI / tests。
  • risk_level：low / medium / high。
  • performance_profile：latency / memory / throughput。
function map_elites_update(candidate):
    cell = feature_map(candidate)
    current = archive[cell]

    if current is empty:
        archive[cell] = candidate
    else if fitness(candidate) > fitness(current):
        archive[cell] = candidate

function island_migration(islands):
    every K generations:
        migrants = export_top_pareto_and_novelty(islands)
        for island in islands:
            island.import_and_reevaluate(migrants)

Islands 可以按目标拆分：performance、correctness、simplicity、security、exploration。 每个 island 用自己的 mutation policy 和 evaluator profile，周期性迁移 elites。

NSGA-II / Pareto 多目标选择

代码 patch 往往无法被一个分数完整表达。NSGA-II 用非支配排序和 crowding distance 保留 Pareto front，让不同 trade-off 区域都有候选。 

x dominates y if:
    x is no worse than y on all objectives
    and better than y on at least one objective
function nsga2_select(candidates, population_size):
    fronts = fast_non_dominated_sort(candidates)
    next_population = []

    for front in fronts:
        compute_crowding_distance(front)
        if size(next_population) + size(front) <= population_size:
            next_population += front
        else:
            sort front by crowding_distance desc
            fill remaining slots from front
            break

    return next_population

对 viben evo，Pareto 目标可以是 correctness、performance、maintainability、diff risk、cost。 最终合并仍可由人工或 policy 从 Pareto archive 中选择。

Memory / Reflexion / Voyager / DGM 记忆、技能库与自改进

Reflexion 把测试结果、错误和外部反馈转成 reflection，进入 episodic memory； Voyager 把成功行为沉淀为可执行 skill library；DGM 维护 agent archive， 让 agent 版本在 sandbox 和 benchmark 中自我改进。

  1. 记录 trajectory：prompt、工具调用、diff、测试、score。
  2. 抽取 memory candidate：失败模式、成功策略、可复用 skill。
  3. 验证候选：回放、A/B eval、跨任务验证。
  4. 归因 credit：idea、skill、memory、trajectory step。
  5. 写入 archive：active / quarantined / deprecated。
  6. 检索注入：按任务、错误签名、repo、成功率选择记忆。
async function evo_memory_loop(task):
    memories = retrieve_active_memories(task)
    skills = retrieve_verified_skills(task)

    trajectory = run_agent(task, { memories, skills })
    eval_result = evaluate_trajectory(trajectory)

    candidates = extract_memory_candidates(
        task, trajectory, eval_result
    )

    for memory in candidates:
        validation = validate_memory(memory)
        save_memory({
            ...memory,
            status: validation.passed ? "active" : "quarantined",
            confidence: validation.confidence,
            evidence_ids: [trajectory.id, validation.id]
        })

    credits = assign_credit(trajectory, eval_result, memories, skills)
    save_credit_records(credits)

防污染规则：新记忆先进入 candidate；无证据不注入 prompt；长期未复用或近期导致失败的记忆降权； repo-specific memory 不默认提升为 global；每次 prompt 注入哪些 memory 都写入 trajectory，失败后可回滚污染源。

4. 代码自我进化系统对比

现有系统的共同点是 evaluator-first：LLM 负责产生候选代码，确定性或半确定性评估器负责筛选， archive/database 负责保存高分与多样性样本，再把这些样本喂回下一轮 prompt。

系统 核心闭环 Memory / Archive 给 viben evo 的启发
FunSearch LLM 生成程序变体，systematic evaluator 打分，搜索“能产生好答案的程序”。 program database、islands、历史高分程序采样。 先定义 seed、evaluator、score、archive，再追求复杂并发。
AlphaEvolve LLM ensemble 直接修改算法/代码，自动 evaluator 验证，进化式保留强候选。 program database + prompt sampler + evaluator feedback。 把产品代码目标转成可量化 score，避免只有主观 LLM review。
OpenEvolve 开源 AlphaEvolve 风格实现，包含 controller、LLM ensemble、evaluator、program database。 MAP-Elites + islands + artifacts feedback。 最值得直接对标：checkpoint、并行 worker、多目标 metrics、可视化、resume。
SWE-agent 通过 agent-computer interface 让模型在真实仓库中搜索、编辑、运行测试。 trajectory/logs 为主，不是进化 archive。 适合作为执行层参考：限制工具、压缩反馈、提高编辑可恢复性。
Darwin Gödel Machine 从 archive 采样 agent，让 agent 修改自身代码并通过 benchmark 验证。 agent lineage tree，保留多个 self-improving path。 长期方向；短期不要直接自改 planner，先让 evo 策略可配置、可审计。

6. 推荐的搜索管理策略

关键不是让模型“更努力地生成 idea”，而是让 controller 学会把预算投给预期收益最高、但仍保留不确定性探索价值的分支。

Controller

候选选择分数

value(node, idea) =
  predicted_delta_score
  + exploration_bonus
  + novelty_bonus
  + memory_match_bonus
  - risk_penalty
  - eval_cost_penalty

这相当于把 UCB、BO acquisition、MAP-Elites novelty 和工程风险合成一个调度分数。

Evaluation

分层预算

  1. Level 0：静态检查、diff 风险、格式与 AST parse。
  2. Level 1：typecheck、受影响测试、核心 CLI smoke test。
  3. Level 2：package tests、targeted benchmark、LLM reviewer。
  4. Level 3：全量 build、E2E、性能回归、人工审批。

一次迭代的建议流程

阶段 动作 算法 输出
Expand 从多个 codebase node 生成 idea，不只从最新 winner 生成。 MCTS + memory retrieval candidate_plan[]
Rollout 为高价值 idea fork 多份，由不同 agent/model/prompt 实现。 Bandit 分配 agent arms candidate_patch[]
Early Stop 低成本评估失败即停止，强候选进入下一层。 Successive Halving survivors[]
Select 先按 idea 聚合 rollout，再做全局选择；保留非 winner elites。 PPO-style + MAP-Elites winner 与 archive
Learn 把 score delta 归因到 idea、operator、模块、agent。 Credit assignment memory.md/jsonl

7. 记忆与 DP 表设计

记忆不应只是“把高分 idea 写进 prompt”。它应该像动态规划表一样保存子问题求解结果，支持剪枝、复用和归因。 对代码库进化来说，记忆至少需要三层：candidate archive、idea credit table、retrieval summary。

Archive

候选版本记忆

保存每个 codebase node 的 parent、patch、score、评估日志、artifacts 和 lineage。

Credit

Idea 归因记忆

按 idea/operator/module 统计 delta_score、成功率、风险、适用条件。

检索摘要记忆

剪枝规则： 如果某类 idea 在相似模块、相似 evaluator、相似 diff budget 下连续低收益，就降低展开概率； 如果 idea 分数高但风险也高，不删除，而是放入高风险 island，等待更合适的 parent 或更强 evaluator。

8. 对 viben evo 的落地路线

阶段 范围 验收标准
MVP 保留当前 viben evo 流程，新增 graph.jsonl、idea-credit.jsonl 和 summaries。 每个 task reward 能归因到 idea；下一轮 idea prompt 能引用 top positive/negative memories。
预算调度 实现 evaluation ladder 与 early-stop 状态，不同候选可停在不同评估层级。 同样 wall-clock 下，评估更多 idea，完整评估集中在高潜力候选。
搜索图 允许从任意 archive node 展开，而不是只能从最新 merged winner 展开。 报告中能展示多条 lineage，并解释为什么选择某个 parent 继续。
MAP-Elites 按模块、改动类型、风险等级、目标指标建立 elites cells。 archive 不只保存一个 best_task，而是保存多个有代表性的 stepping stones。
策略自进化 让 evo 策略参数、prompt、operator 可被受限修改和评估。 只允许在 sandbox/worktree 内修改策略；人工审批后才进入默认策略。
不要过早做的事： 不要在 evaluator 还弱时允许系统自动修改自己的 planner 或 reward 权重。 否则最容易进化出“骗分”的 patch，而不是更好的代码库。
