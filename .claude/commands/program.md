# 自动研究

这是一个让 LLM 自主进行研究的实验项目。

## 设置

要设置新实验，请与用户协作完成以下步骤：

1. **确定运行标签**：根据当天日期提议一个标签（例如 `mar5`）。分支 `autoresearch/<tag>` 必须不存在——这是一次全新的运行。
2. **创建分支**：从当前 master 执行 `git checkout -b autoresearch/<tag>`。
3. **阅读相关文件**：仓库很小。阅读以下文件以获取完整上下文：
   - `README.md` — 仓库上下文。
   - `prepare.py` — 固定常量、数据准备、分词器、数据加载器、评估。不可修改。
   - `train.py` — 你要修改的文件。模型架构、优化器、训练循环。
4. **验证数据存在**：检查 `~/.cache/autoresearch/` 是否包含数据分片和分词器。如果没有，告知用户运行 `uv run prepare.py`。
5. **初始化 results.tsv**：创建只包含表头行的 `results.tsv`。基线将在第一次运行后记录。
6. **确认并开始**：确认设置正确。

获得确认后，启动实验。

## 实验流程

每个实验在单个 GPU 上运行。训练脚本运行 **固定时间预算 5 分钟**（墙钟训练时间，不包括启动/编译）。启动方式很简单：`uv run train.py`。

**你可以做的事情：**
- 修改 `train.py` — 这是你唯一需要编辑的文件。一切都可以改：模型架构、优化器、超参数、训练循环、批量大小、模型规模等。

**你不能做的事情：**
- 修改 `prepare.py`。它是只读的。它包含固定的评估、数据加载、分词器和训练常量（时间预算、序列长度等）。
- 安装新包或添加依赖。你只能使用 `pyproject.toml` 中已有的内容。
- 修改评估工具。`prepare.py` 中的 `evaluate_bpb` 函数是基准指标。

**目标很简单：获得最低的 val_bpb。** 由于时间预算是固定的，你不需要担心训练时间——始终是 5 分钟。一切都可以改：架构、优化器、超参数、批量大小、模型规模。唯一的约束是代码能够运行且在时间预算内完成。

**显存**是软约束。为了有意义的 val_bpb 提升，适度增加是可以接受的，但不应大幅膨胀。

**简洁性原则**：在其他条件相同的情况下，越简单越好。增加丑陋复杂性的小改进不值得。相反，删除某些东西并获得相同或更好的结果是很好的结果——这是简化的胜利。评估是否保留更改时，要权衡复杂性成本与改进幅度。0.001 val_bpb 的改进但增加了 20 行 hack 代码？可能不值得。通过删除代码获得 0.001 val_bpb 改进？绝对保留。改进约为 0 但代码更简单？保留。

**第一次运行**：你的第一次运行应该始终是建立基线，所以你将按原样运行训练脚本。

## 输出格式

脚本完成后会打印如下摘要：

```
---
val_bpb:          0.997900
training_seconds: 300.1
total_seconds:    325.9
peak_vram_mb:     45060.2
mfu_percent:      39.80
total_tokens_M:   499.6
num_steps:        953
num_params_M:     50.3
depth:            8
```

注意脚本配置为始终在 5 分钟后停止，因此根据计算机的计算平台，数字可能看起来不同。你可以从日志文件中提取关键指标：

```
grep "^val_bpb:" run.log
```

## 记录结果

实验完成后，将其记录到 `results.tsv`（制表符分隔，不是逗号分隔——逗号会破坏描述）。

TSV 有表头行和 5 列：

```
commit	val_bpb	memory_gb	status	description
```

1. git commit 哈希（短格式，7 字符）
2. 达到的 val_bpb（例如 1.234567）— 崩溃时使用 0.000000
3. 峰值内存（GB），保留一位小数（例如 12.3 — 将 peak_vram_mb 除以 1024）— 崩溃时使用 0.0
4. 状态：`keep`、`discard` 或 `crash`
5. 简短描述这个实验尝试了什么

示例：

```
commit	val_bpb	memory_gb	status	description
a1b2c3d	0.997900	44.0	keep	baseline
b2c3d4e	0.993200	44.2	keep	increase LR to 0.04
c3d4e5f	1.005000	44.0	discard	switch to GeLU activation
d4e5f6g	0.000000	0.0	crash	double model width (OOM)
```

## 实验循环

实验在专用分支上运行（例如 `autoresearch/mar5` 或 `autoresearch/mar5-gpu0`）。

永久循环：

1. 查看 git 状态：我们当前所在的分支/提交
2. 通过直接修改代码，用实验想法调整 `train.py`
3. git commit
4. 运行实验：`uv run train.py > run.log 2>&1`（重定向所有输出——不要使用 tee 或让输出淹没你的上下文）
5. 读取结果：`grep "^val_bpb:\|^peak_vram_mb:" run.log`
6. 如果 grep 输出为空，运行崩溃了。运行 `tail -n 50 run.log` 读取 Python 堆栈跟踪并尝试修复。如果多次尝试后仍无法正常运行，放弃。
7. 在 tsv 中记录结果（注意：不要提交 results.tsv 文件，让它保持未跟踪状态）
8. 如果 val_bpb 改善（更低），你"推进"分支，保留 git commit
9. 如果 val_bpb 相同或更差，你 git reset 回到起点

这个想法是你是一个完全自主的研究者，尝试各种方法。如果有效，保留。如果无效，丢弃。你在推进分支以便迭代。如果你觉得陷入某种困境，你可以回退，但这应该非常非常谨慎地使用（如果有的话）。

**超时**：每个实验大约需要 5 分钟（+ 几秒钟的启动和评估开销）。如果运行超过 10 分钟，终止它并视为失败（丢弃并回退）。

**崩溃**：如果运行崩溃（OOM、bug 等），使用你的判断：如果是愚蠢且容易修复的问题（例如拼写错误、缺少 import），修复它并重新运行。如果想法本身从根本上是有问题的，直接跳过它，在 tsv 中记录"crash"状态，然后继续。

**永不停止**：一旦实验循环开始（在初始设置之后），不要暂停询问用户是否应该继续。不要问"我应该继续吗？"或"这是一个好的停止点吗？"。用户可能在睡觉，或离开电脑，期望你*无限期*地继续工作直到被手动停止。你是自主的。如果你没有想法了，更努力地思考——阅读代码中引用的论文，重新阅读相关文件寻找新角度，尝试组合之前的接近成功的尝试，尝试更激进的架构变化。循环一直运行直到用户中断你，就是这样。

作为示例用例，用户可能在睡觉时让你运行。如果每个实验大约需要 5 分钟，那么你可以每小时运行约 12 次，在平均人类睡眠期间总共约 100 次。然后用户醒来看到实验结果，全部由你在他们睡觉时完成！
