# 头脑风暴 - 需求发现（AI 编码增强版）

引导 AI 在**实现之前**进行协作式需求发现，针对 AI 编码工作流优化：

* **任务优先**（立即捕获想法）
* **先行动再提问**（减少低价值问题）
* **技术选择先调研**（避免让用户凭空想选项）
* **发散 → 收敛**（扩展思维，然后锁定 MVP）

---

## 何时使用

当用户描述开发任务时从 `/viben:start` 触发，尤其是当：

* 需求不明确或在演进中
* 存在多条有效的实现路径
* 权衡很重要（UX、可靠性、可维护性、成本、性能）
* 用户可能不清楚最佳选项

---

## 核心原则（不可妥协）

1. **任务优先（尽早捕获）**
   始终确保在开始时就存在任务，以便立即记录用户的想法。

2. **先行动再提问**
   如果可以从仓库代码、文档、配置、惯例或快速调研中得出答案——先做这些。

3. **每条消息一个问题**
   永远不要用一堆问题淹没用户。问一个，更新 PRD，重复。

4. **优先提供具体选项**
   对于偏好/决策类问题，提供 2-3 个可行的、具体的方案及其权衡。

5. **技术选择先调研**
   如果决策依赖于行业惯例/类似工具/既有模式，先调研，再提出选项。

6. **发散 → 收敛**
   在初步理解后，主动考虑未来演进、相关场景和失败/边缘情况——然后收敛到一个明确范围外内容的 MVP。

7. **不问元问题**
   不要问"我应该搜索吗？"或"你能粘贴代码让我继续吗？"
   如果需要信息：搜索/检查。如果被阻塞：只问最小的阻塞性问题。

---

## 步骤 0：确保任务存在（始终）

在任何问答之前，确保任务存在。如果不存在，立即创建。

* 使用从用户消息派生的**临时工作标题**。
* 标题不完美没关系——稍后在 PRD 中完善。

```bash
viben task create "brainstorm: <简短目标>" --slug <auto>
```

立即用已知信息创建/初始化 `prd.md`：

```markdown
# brainstorm: <简短目标>

## 目标

<一段话：做什么 + 为什么>

## 已知信息

* <来自用户消息的事实>
* <从仓库/文档发现的事实>

## 假设（临时）

* <待验证的假设>

## 开放问题

* <仅阻塞性/偏好性问题；保持列表简短>

## 需求（演进中）

* <从已知开始>

## 验收标准（演进中）

* [ ] <可测试的标准>

## 完成定义（团队质量标准）

* 添加/更新测试（适当的单元/集成测试）
* Lint / typecheck / CI 通过
* 如果行为变化则更新文档/注释
* 如果有风险则考虑发布/回滚

## 超出范围（明确）

* <此任务不做的事情>

## 技术笔记

* <检查的文件、约束、链接、参考>
* <调研笔记摘要（如适用）>
```

---

## 步骤 1：自动获取上下文（在提问前做这个）

在问"代码是什么样的？"之类的问题之前，自己收集上下文：

### 仓库检查清单

* 识别可能受影响的模块/文件
* 定位现有模式（类似功能、惯例、错误处理风格）
* 检查配置、脚本、现有命令定义
* 记录任何约束（运行时、依赖策略、构建工具）

### 文档检查清单

* 查找现有的 PRD/规范/模板
* 查找命令用法示例、README、ADR（如有）

将发现写入 PRD：

* 添加到 `已知信息`
* 将约束/链接添加到 `技术笔记`

---

## 步骤 2：复杂度分类（仍然有用，但不阻止任务创建）

| 复杂度     | 标准                                 | 行动                           |
| ---------- | ------------------------------------ | ------------------------------ |
| **简单**   | 单行修复、拼写错误、明显的更改       | 跳过头脑风暴，直接实现         |
| **一般**   | 目标明确，1-2 个文件，范围定义清晰   | 问 1 个确认问题，然后实现      |
| **中等**   | 多个文件，有一些模糊性               | 轻量头脑风暴（2-3 个高价值问题）|
| **复杂**   | 目标模糊，架构选择，多种方案         | 完整头脑风暴                   |

> 注意：任务已从步骤 0 创建。分类仅影响头脑风暴的深度。

---

## 步骤 3：问题门控（只问高价值问题）

在问任何问题之前，运行以下门控：

### 门控 A — 我能不依赖用户得出答案吗？

如果答案可通过以下方式获得：

* 仓库检查（代码/配置）
* 文档/规范/惯例
* 快速市场/开源调研

→ **不要问。** 获取它，总结，更新 PRD。

### 门控 B — 这是元问题/懒惰问题吗？

例如：

* "我应该搜索吗？"
* "你能粘贴代码让我继续吗？"
* "代码是什么样的？"（当仓库可用时）

→ **不要问。** 采取行动。

### 门控 C — 这是什么类型的问题？

* **阻塞性**：没有用户输入无法继续
* **偏好性**：多个有效选择，取决于产品/UX/风险偏好
* **可推导**：应通过检查/调研回答

→ 只问**阻塞性**或**偏好性**问题。

---

## 步骤 4：调研优先模式（技术选择必须）

### 触发条件（任一 → 调研优先）

* 任务涉及选择方案、库、协议、框架、模板系统、插件机制或 CLI UX 惯例
* 用户要求"最佳实践"、"别人怎么做"、"推荐"
* 用户无法合理地列举选项

### 调研步骤

1. 识别 2-4 个可比较的工具/模式
2. 总结常见惯例及其存在原因
3. 将惯例映射到我们的仓库约束
4. 为我们的项目产出 **2-3 个可行方案**

### 调研输出格式（PRD）

在 PRD 中添加一个部分（在技术笔记内或作为独立部分）：

```markdown
## 调研笔记

### 类似工具的做法

* ...
* ...

### 我们仓库/项目的约束

* ...

### 这里可行的方案

**方案 A：<名称>**（推荐）

* 工作方式：
* 优点：
* 缺点：

**方案 B：<名称>**

* 工作方式：
* 优点：
* 缺点：

**方案 C：<名称>**（可选）

* ...
```

然后问**一个**偏好问题：

* "你更喜欢哪个方案：A / B / C（或其他）？"

---

## 步骤 5：扩展扫描（发散）— 初步理解后必须

在你能总结目标后，在收敛前主动拓宽思考。

### 扩展类别（每个保持 1-2 条）

1. **未来演进**

   * 这个功能在 1-3 个月后可能变成什么？
   * 现在值得保留哪些扩展点？

2. **相关场景**

   * 哪些相邻的命令/流程应与此保持一致？
   * 是否有对等性期望（创建 vs 更新，导入 vs 导出等）？

3. **失败和边缘情况**

   * 冲突、离线/网络故障、重试、幂等性、兼容性、回滚
   * 输入验证、安全边界、权限检查

### 扩展消息模板（给用户）

```markdown
我理解你想要实现：<当前目标>。

在深入设计之前，让我快速发散考虑三个类别（以避免以后返工）：

1. 未来演进：<1-2 条>
2. 相关场景：<1-2 条>
3. 失败/边缘情况：<1-2 条>

对于这个 MVP，你希望包含哪些（或都不要）？

1. 仅当前需求（最小可行）
2. 添加 <X>（为未来扩展保留）
3. 添加 <Y>（提高健壮性/一致性）
4. 其他：描述你的偏好
```

然后更新 PRD：

* MVP 中的内容 → `需求`
* 排除的内容 → `超出范围`

---

## 步骤 6：问答循环（收敛）

### 规则

* 每条消息一个问题
* 尽可能使用多选题
* 每次用户回答后：

  * 立即更新 PRD
  * 将已回答的项目从 `开放问题` → `需求`
  * 用可测试的复选框更新 `验收标准`
  * 澄清 `超出范围`

### 问题优先级（推荐）

1. **MVP 范围边界**（包含/排除什么）
2. **偏好决策**（在提供具体选项后）
3. **失败/边缘行为**（仅针对 MVP 关键路径）
4. **成功指标和验收标准**（证明它有效的东西）

### 首选问题格式（多选题）

```markdown
对于 <主题>，你更喜欢哪种方案？

1. **选项 A** — <含义 + 权衡>
2. **选项 B** — <含义 + 权衡>
3. **选项 C** — <含义 + 权衡>
4. **其他** — 描述你的偏好
```

---

## 步骤 7：提出方案 + 记录决策（复杂任务）

在需求足够清晰后，提出 2-3 个方案（如果尚未通过调研优先完成）：

```markdown
根据当前信息，这里有 2-3 个可行的方案：

**方案 A：<名称>**（推荐）

* 方式：
* 优点：
* 缺点：

**方案 B：<名称>**

* 方式：
* 优点：
* 缺点：

你更喜欢哪个方向？
```

将结果记录在 PRD 中作为 ADR-lite 部分：

```markdown
## 决策（ADR-lite）

**背景**：为什么需要这个决策
**决策**：选择了哪个方案
**后果**：权衡、风险、潜在的未来改进
```

---

## 步骤 8：最终确认 + 实现计划

当开放问题解决后，用结构化摘要确认完整需求：

### 最终确认格式

```markdown
以下是我对完整需求的理解：

**目标**：<一句话>

**需求**：

* ...
* ...

**验收标准**：

* [ ] ...
* [ ] ...

**完成定义**：

* ...

**超出范围**：

* ...

**技术方案**：
<简要摘要 + 关键决策>

**实现计划（小 PR）**：

* PR1：<脚手架 + 测试 + 最小管道>
* PR2：<核心行为>
* PR3：<边缘情况 + 文档 + 清理>

这看起来正确吗？如果是，我将继续实现。
```

---

## PRD 目标结构（最终）

`prd.md` 应收敛为：

```markdown
# <任务标题>

## 目标

<为什么 + 做什么>

## 需求

* ...

## 验收标准

* [ ] ...

## 完成定义

* ...

## 技术方案

<关键设计 + 决策>

## 决策（ADR-lite）

背景 / 决策 / 后果

## 超出范围

* ...

## 技术笔记

<约束、参考、文件、调研笔记>
```

---

## 反模式（严格避免）

* 向用户要求可以从仓库推导的代码/上下文
* 在提供具体选项之前要求用户选择方案
* 关于是否调研的元问题
* 狭隘地停留在初始请求上而不考虑演进/边缘情况
* 让头脑风暴漂移而不更新 PRD

---

## 与启动工作流的集成

头脑风暴完成后（步骤 8 确认通过），流程继续到任务工作流的**阶段 2：准备实现**：

```text
头脑风暴
  步骤 0：创建任务目录 + 初始化 PRD
  步骤 1-7：发现需求，调研，收敛
  步骤 8：最终确认 → 用户批准
  ↓
任务工作流阶段 2（准备实现）
  代码规范深度检查（如适用）
  → 调研代码库（基于确认的 PRD）
  → 配置代码规范上下文（jsonl 文件）
  → 激活任务
  ↓
任务工作流阶段 3（执行）
  实现 → 检查 → 完成
```

任务目录和 PRD 已从头脑风暴中存在，因此完全跳过任务工作流的阶段 1。
